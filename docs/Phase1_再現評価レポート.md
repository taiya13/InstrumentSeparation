# Phase 1 再現・評価レポート — 既存ベースモデルの再現と限界把握（PoC）

**目的**: 新しいAIは作らない。**現在の世界最高水準の音源分離を正確に再現し、その性能と限界を客観的に把握する**。
**日付**: 2026-07 / **ステータス**: PoC 実行完了
**実行環境**: CPU 4コア / RAM 15GB / **GPU 無し** / Python 3.11.15 / ネットワークは制限ポリシー下

---

## 0. エグゼクティブサマリー

- **採用ベースモデル**: Phase 1 の再現対象は **HT-Demucs（Demucs v4, MIT）**。理由は「実際に動かせる・MIT・CPUでも推論可・6ステム実績・エコシステム最大」。**Phase 2 以降の本命バックボーンは Mel-Band RoFormer** と位置づけ、比較用に併記。
- **この開発サンドボックスの重大な制約を実測で確認**: モデル重みの配布 CDN（Facebook / HuggingFace / PyTorch / Zenodo）が **egress ポリシーで全てブロック**。→ **本物の学習済み Demucs/RoFormer をこの環境ではダウンロードできず、そのままの実分離は回せない**。pypi と GitHub は到達可。
- そこで本 PoC は、**重み不要で本質を測れる実験**を実際に実行した:
  1. **制御された合成オーケストラ**（13楽器・正解ステム付き）を生成。
  2. **オラクル・マスク（理想比マスク）による分離上限**を測定 → これは*どんな*マスク型モデル（Spleeter/UMX/MDX/Demucs/RoFormer）でも超えられない**モデル非依存の天井**。
  3. **同一楽器 2×2 診断実験**で「いつ分離が原理的に不可能になるか」を定量化。
  4. **HT-Demucs（torchaudio 実装, 83.6M params）を CPU で動作確認**（推論パイプラインが動くこと・計算コストを実測）。
- **最重要の実測結果（モデル非依存）**: 「**同一音色＋同一音高（ユニゾン/セクション重複）**」の分離は、**理想オラクルですら SI-SDRi ≈ 0.26 dB**（＝ほぼ不可能）。一方、音色か音高のどちらかが違えば 6〜8 dB に跳ね上がる。**第1/第2ヴァイオリンの重複は現行のマスク型分離の原理的限界の外**であることが数値で確定した。
- **推論に GPU は不要**（HDemucs は CPU で RTF≈0.16–0.42x、RAM 1.5GB）。**GPU が本質的に要るのは学習**と実運用のバッチ高速化。

## 1. ベースモデルの選定理由

| 観点 | HT-Demucs (Demucs v4) ← Phase1 採用 | Mel-Band RoFormer ← Phase2+ 本命 |
|---|---|---|
| 精度(一般MSS) | 高い | **最高（SOTA）** |
| ライセンス | **MIT** | MIT（lucidrains 再実装 / ZFTurbo 枠組） |
| すぐ動かせるか | **◎（`demucs -n htdemucs_6s file`）** | △（設定・重み準備が必要） |
| CPU 推論 | **可（実測 RTF<1）** | 重い |
| ステム | 4 / 6（+guitar,piano） | 学習次第で拡張 |
| 学習/改造 | ○（公式 dora） | ○（帯域分割が多楽器拡張に好適） |
| コミュニティ | **最大** | 最活発 |

**判断**: Phase 1 の目的は「まず世界最高水準を*動かして*限界を掴む」こと。導入容易性・CPU 実行性・MIT の観点から **HT-Demucs を再現対象**に選定。**Mel-Band RoFormer は Phase 2 で本命バックボーンに採用**する前提で、環境・学習レシピを本リポジトリに用意した（`environment/README.md`）。

## 4. 実験結果（実測値）

### 4-1. オラクル分離の上限（＝マスク型モデルの物理的天井）

合成13楽器・モノ混合に対し、**正解から作った理想比マスク(IRM)**で各音源を取り出したときの SI-SDR 改善量（SI-SDRi, dB）。*これを超える性能を出せるマスク型モデルは存在しない。*

**楽器ファミリー単位（分離しやすい順）**

| ファミリー | SI-SDRi (dB) | 解釈 |
|---|---|---|
| percussion (timpani) | **+21.3** | 打楽器は時間的にまばらで分離容易 |
| brass | **+10.6** | 金管はまとまり分離しやすい |
| woodwinds | **+7.2** | 木管 |
| strings | **+6.4** | 弦は音域が広く重なり多い |

→ **ファミリー単位の分離は原理的に十分可能**（現行技術の延長で到達しやすい）。

**個別楽器単位（抜粋, SI-SDRi）**: timpani +21.2 / trumpet +20.0 / bass +13.7 / oboe +13.8 / violin2 +13.2 / viola +12.8 / clarinet +12.7 / violin1 +11.9 / horn +11.6 / cello +11.4 / trombone +9.6 / bassoon +9.6
（絶対 SI-SDR は 0〜5 dB と低め＝13音源が密に重なる濃いテクスチャのため。改善量は大きいが絶対値は厳しい、というのが濃密オケの現実。）

### 4-2. 同一楽器 2×2 診断（本 PoC の核心・モデル非依存）

2音源の混合で **音高(同/異) × 音色(同/異)** を総当たり。各ケースのオラクル IRM 平均 SI-SDRi:

| ケース | 平均 SI-SDRi | 判定 |
|---|---|---|
| **ユニゾン＋同音色**（第1/第2Vn の重複に相当） | **+0.26 dB** | **理想でもほぼ不可能（原理的な壁）** |
| ユニゾン＋異音色（Vn とフルート同音） | +6.72 dB | 音色差が効く |
| ハーモニー＋同音色（Vn 二部, 3度違い） | +7.17 dB | 音高差が効く |
| ハーモニー＋異音色 | +8.00 dB | 最も容易 |

→ **分離を原理的に殺すのは「同音色かつ音高が重なる」ケースのみ**。これは**セクション重複・ユニゾン**という*オーケストレーションで最も普通に起こる書法*そのもの。**モデルをいくら強くしても、モノ波形からは超えられない**ことが数値で確定。

### 4-3. 重み不要ブラインド手法（HPSS）の実性能

| 手法 | 対象 | SI-SDRi |
|---|---|---|
| HPSS 打楽器抽出 | timpani | **−3.4 dB（混合より悪化）** |

→ 古典的ブラインド手法は、旋律的なティンパニ＋多数の音の立ち上がりが混在する濃いオケでは**破綻**。学習ベースが必要な理由を裏付ける。

### 4-4. HT-Demucs アーキテクチャの CPU 動作確認

| 指標 | 実測 |
|---|---|
| パラメータ数 | 83.6 M |
| CPU 推論 (6s ステレオ@44.1kHz) | 約 1.0–1.8 s（**RTF 0.16–0.42x, リアルタイムより速い**） |
| ピーク RAM | 約 1.5 GB |
| CUDA | 不使用（CPU 実行） |

→ **推論は GPU 無しでも実用速度**で回る（＝Phase 2 の推論配布は CPU でも可）。GPU が要るのは学習側。

> 注: この動作確認は**ランダム重み**（本物の重みは DL ブロック）。出力は分離ではなく、**「実装が CPU で構築・順伝播できること」と「計算コスト」**の確認が目的。

## 5. 分離結果・性能評価（オーケストラ音源での所見）

正解付き合成オケ＋オラクル上限という枠組みから、**現行マスク型分離が到達しうる品質**を評価した。

- **よく分離できる楽器**: 時間的にまばら or 音色が際立つもの（**ティンパニ、トランペット、フルート、コントラバス**）。ファミリー単位は全て良好（+6〜+21 dB）。
- **分離が難しい/混ざりやすい楽器**: **中音域に密集する内声**（**ヴィオラ、チェロ、ファゴット、トロンボーン**）は絶対 SI-SDR が低い。**第1/第2ヴァイオリンの重複は理想でも不可能**（4-2）。
- **ノイズ**: HPSS 等ブラインド手法は広帯域の漏れ（bleed）が大きい。
- **アーティファクト**: マスク型は混合位相を流用するため、重複帯域で**ミュージカルノイズ・にじみ**が不可避。オラクルでも絶対 SI-SDR が伸びないのはこの重なりが原因。
- **現時点で到達できる品質（総括）**:
  - ファミリー分離（弦/木管/金管/打）= **実用手前レベルで可能**。
  - 音色が際立つ独奏楽器の抽出 = **条件付きで可能**。
  - **同一セクション（Vn I/II 等）の分割 = モノ音源では原理的に不可能**。空間 or 楽譜の追加情報が必須。

## 6. ボトルネック分析

### モデルの問題
- **マスク型（周波数マスク）にはモデル非依存の天井**があり、同音色ユニゾンは超えられない（4-2 で実証）。→ 波形型/生成型や**マルチチャンネル・楽譜条件付け**が必要。
- **既存の学習済みモデルにはオーケストラ楽器の出力が存在しない**。ポップ学習の SOTA にオケを入れると、全楽器が "other" に潰れる（`run_demucs_reference.py` が定量化する構図）。

### データセットの問題（最大の制約）
- **ブリードなしのフルオーケストラ・マルチトラック実録が存在しない**。
- 学習は合成に依存 → **合成→実録のドメインギャップ**。
- 本 PoC の合成ベンチも**合成である点が限界**（実録の残響・奏法の多様性を欠く）。数値は「上限の構造」を示すが実録の絶対値ではない。
- 加えてこの環境では **SynthSOD 等のデータ入手自体がブロック**され、実データ実験は GPU 箱に持ち越し。

### 学習方法の問題
- この環境は **GPU 無し → 学習不可**（レシピのみ提供）。
- **オーケストラ用のステム定義**（弦/木管/…→楽器→セクションの階層）が前例に乏しく、独自設計が必要。
- 同一楽器を分けるには**楽譜アライメント/空間情報を条件に組み込む学習**が必要（既存の固定ステム学習では不可能）。

## 7. 次の Phase で改良すべき項目

1. **オーケストラ・ステムでの学習**（まず弦/木管/金管/打の4系統 → 音色が異なる楽器へ）。ベース: Mel-Band RoFormer（ZFTurbo 枠組）。
2. **実データの確保と評価**: SynthSOD / EnsembleSet / CocoChorales で学習、**URMP / Aalto / Cadenza** で実録評価（GPU＋自由ネットワークの環境で）。
3. **合成→実録ドメイン適応**: 残響・強弱・マイク特性の augmentation、fine-tune、自己教師。
4. **同一楽器問題への追加情報**（Phase 4 研究トラック）: **マルチチャンネル/空間手がかり**または **score-informed 条件付け**（本 PoC が「モノでは不可能」を数値で示したため、ここは既存流用ではなく独自研究が必須と確定）。
5. **query 条件付け（Banquet 型）**で出力楽器を柔軟に拡張。
6. **独自データ整備**: ブリードなしオケ・マルチトラック（合成の高度化＋自前実録）。プロジェクト最大の差別化点。
7. **本物の SOTA の実分離ベースライン取得**: 本リポジトリの `run_demucs_reference.py` を GPU 箱で回し、ポップ SOTA がオケでどう振る舞うかの実測を Phase 1 の数値に追記。

## 9. 結論

- **世界最高水準の「アーキテクチャ」は再現・CPU 実行まで確認**した（HT-Demucs 83.6M, 動作OK）。**学習済み重みの取得だけがこの環境の制約でブロック**され、実分離は GPU＋自由ネットワークのマシンに持ち越し（レシピは完備）。
- **より重要な成果**として、**「到達可能な品質の天井」をモデル非依存のオラクルで実測**し、**同一音色ユニゾンの分離が原理的に不可能（+0.26 dB）**であることを定量的に確定した。これは Phase 0 の中心的主張の実証であり、**「独自開発が必須なのは同一楽器分離であり、そこはモノ音源＋マスク型では絶対に解けない＝空間/楽譜情報が要る」**という設計判断を数値で裏付ける。
- 次は **Phase 2: オーケストラ・ステム学習（ファミリー分離）** を、GPU 環境で本リポジトリのレシピに沿って着手することを推奨する。
